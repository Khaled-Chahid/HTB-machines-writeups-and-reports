# Machine : Bashed - HTB Labs

## Assessment Summary

A publicly accessible development directory exposed a web shell (`phpbash`) that provided unauthenticated remote code execution as the web service account. From this foothold, a passwordless `sudo` entry allowed a pivot to the `scriptmanager` account, whose writable script directory was executed periodically by `root` via a cron job. Replacing the script's output file with a malicious payload resulted in code execution as `root`.

**Scope:** 10.10.10.68 in the HTB lab. This report is based on the supplied official writeup; the findings were not independently retested.

| ID | Finding | Severity |
|---|---|---|
| CRJ-01 | Exposed `/dev` directory containing a web shell | Critical |
| CRJ-02 | Passwordless `sudo` access to the `scriptmanager` account | Medium |
| CRJ-03 | Root-owned cron job executing a script writable by `scriptmanager` | High |

---

### CRJ-01 — Exposed Development Directory Containing a Web Shell

**Affected service:** Apache HTTP (port 80).

Directory fuzzing against the web root discovered a `/dev` directory that had been left publicly accessible. It contained `phpbash`, a fully interactive PHP web shell, reachable by any unauthenticated visitor.

**Verification:** `ffuf` directory fuzzing with a SecLists wordlist identified `/dev`. Browsing to `http://10.10.10.68/dev` exposed `phpbash`, which was used to execute a Python reverse shell, returning an interactive session on the host.

**Impact:** Unauthenticated remote code execution as the web service account. This is the initial foothold that made every subsequent finding possible.

**Remediation:** Remove development and debugging tools, including web shells, from production web roots before deployment. Enforce a deployment process that excludes `/dev`, test, and build artifacts from publicly served directories. Periodically audit the web root with directory-enumeration tooling as part of routine hardening checks.

---

### CRJ-02 — Passwordless Sudo Access to the `scriptmanager` Account

**Affected component:** `sudoers` configuration for the web service account.

The compromised web service account held a NOPASSWD `sudo` rule permitting an interactive shell switch to the `scriptmanager` account, with no further authentication required.

**Verification:** `sudo -l` listed the rule; `sudo -u scriptmanager /bin/bash` succeeded without a password prompt, confirming the account switch.

**Impact:** Any attacker who compromises the web service account inherits full control of `scriptmanager`, including whatever file and script access that account holds — directly enabling CRJ-03.

**Remediation:** Avoid granting NOPASSWD `sudo` rules for account switching unless strictly required. Where such delegation is necessary, scope it to the minimum commands needed rather than a full shell, and require authentication.

---

### CRJ-03 — Root Cron Job Executing a Script Writable by a Lower-Privileged User

**Affected component:** Scheduled task owned by `root`, operating on files under `/scripts` (writable by `scriptmanager`).

A script under `/scripts`, owned and controlled by `scriptmanager`, was observed producing an output file (`test.txt`) on a recurring interval with no corresponding manual execution. Deleting the file and observing its automatic recreation after about a minute confirmed it was being regenerated by a `root`-owned cron job. Since `scriptmanager` had write access to the script's directory, a malicious script dropped in its place was executed by `root` on the next cron run.

**Verification:** A Python reverse-shell payload was written to the `scripts` directory as `exploit.py` (named without a leading dot, since cron ignores hidden files). After roughly one minute, the cron job executed it, returning a shell owned by `root`. `crontab -l` was subsequently used to confirm the scheduled task.

**Impact:** Complete compromise of the host. A privileged scheduled task operating on a directory writable by a lower-privileged account is equivalent to granting that account root access.

**Remediation:** Ensure scripts and directories executed by privileged cron jobs are owned by and writable only by `root` (or an equivalently trusted account), never by the account that triggers or manages them. Apply the principle of least privilege to scheduled tasks, and audit `crontab` entries and their target file permissions as part of routine host hardening.

---

### Remediation Priority

First remove the exposed `/dev` web shell to eliminate the unauthenticated entry point (CRJ-01). Then remove the NOPASSWD `sudo` rule for `scriptmanager` to break the pivot path (CRJ-02). Finally, correct the ownership and permissions on the cron-executed script directory so `scriptmanager` can no longer influence what `root` executes (CRJ-03). Verify remediation by confirming the web root no longer serves development tools, reviewing all `sudoers` entries, and auditing file permissions on every directory referenced by a root-owned cron job.
